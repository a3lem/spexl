## Context

The SDD plugin currently relies entirely on the AI agent for file operations -- creating directories, writing JSON, moving folders, parsing markdown headings. spectl replaces the mechanical parts with a Python CLI distributed alongside the plugin. The agent calls `spectl` via Bash tool calls.

Python was chosen.

## Goals / Non-Goals

**Goals:**
- Single-file Python script, no external dependencies beyond the standard library
- Each command does one thing and exits -- no interactive modes
- Output is human-readable by default, parseable when needed (`--json`)
- Errors descriptive enough for an AI agent to act on

**Non-Goals:**- Spec content authoring (agent's job)
- Delta-to-reference merging (spec-sync agent's job)
- Anything requiring AI judgment

## Decisions

### Single file, no framework

`spectl` is a single Python file using `argparse` from stdlib. No Click, no Typer, no dependencies. The tool is simple enough that a framework adds nothing.

**Alternatives considered:** Click/Typer would give nicer help text and argument parsing, but add a dependency for a tool with 6 commands and ~15 flags total. Not worth it.

### Distribution as a plugin script

`spectl` lives at `scripts/spectl.py` in the plugin. Invoked via `python3 scripts/spectl.py`.

### Command structure

Six commands: `new`, `changes`, `archived`, `info`, `archive`, `refs`. Listing active and archived changes are separate commands rather than flags on one `list` command -- each does one thing.

### Command dispatch

argparse subparsers with `set_defaults(func=cmd_xxx)`. Each command is a subparser; `main()` resolves the spec root, then calls `args.func(args, root)`. Per-command `--help` comes for free.

### Error handling

Commands raise `SpectlError` for user-facing errors. `main()` catches it, prints to stderr with an `error:` prefix, and exits 1. Error messages include paths, expected vs actual state, and actionable guidance (e.g. "Use --force to archive anyway", "Try --archived to include archived changes").

**Alternatives considered:** `sys.exit(1)` directly in commands -- simpler but harder to test and mixes control flow with error reporting.

### Spec root discovery

Resolved once in `main()` before dispatching. Default: `Path('specs')` relative to cwd. `--dir` overrides with an explicit path to a spec root (e.g. `--dir specs/backend`). Commands that need `changes/` or `reference/` append those to the resolved root.

For `changes -r`, discovery walks down from cwd to find all directories containing a `changes/` subdirectory. `--dir` and `-r` are mutually exclusive.

### Identifier resolution

Commands that operate on a single change (`info`, `archive`) accept a slug, id, or path:
1. If the identifier contains `/`, treat it as a direct path
2. Otherwise, try as a slug (directory name match in `changes/`)
3. Otherwise, scan `.change.json` files for a matching `id`

For `info`, the `--archived` flag extends the scan to `changes/archive/`. For archived slug matching, the date prefix is stripped (matches `*-{slug}`).

### .change.json model

Minimal stored state. Only records what can't be inferred:
- `id`: random 5-character alphanumeric, generated by `spectl new`
- `created`: ISO date, set by `spectl new`
- `archived`: `{"reason": "merged"|"rejected"}`, set by `spectl archive`

No `status` field. Status is computed from artifacts.

### Computed status

`spectl changes` derives status from the filesystem:
- `drafting`: missing any of proposal.md, design.md, tasks.md, or delta specs
- `ready`: all artifacts present, all task checkboxes open
- `in progress`: all artifacts present, mix of open and closed checkboxes
- `complete`: all artifacts present, all checkboxes closed

Status moves backward naturally: reopening a checkbox or adding a new task returns to `in progress`.

### Output formatting

Commands build structured data (dicts/lists). A shared `output(data, formatter, args)` function serializes: `json.dumps` when `--json` is set, otherwise calls a formatter function for human-readable text. Data stays structured until the final render step.

### Archive guard

`spectl archive` blocks with exit 1 if `tasks.md` has incomplete tasks. `--force` overrides. `--rejected` skips the completeness check and sync summary entirely.

### Sync summary parsing

`spectl archive` (and `--dry-run`) counts ADDED/MODIFIED/REMOVED/RENAMED requirements per delta spec. Regex-based heading parsing:
- Scan for `## ADDED Requirements`, `## MODIFIED Requirements`, etc.
- Under each, count `### Requirement:` headings
- For new capabilities, check whether `specs/reference/<name>/` exists

Intentionally shallow -- counts headings, doesn't validate content. The actual merge is the spec-sync agent's job.

## Risks / Trade-offs

Regex-based markdown parsing for sync summary is fragile if spec files deviate from the template structure → Acceptable because the summary is informational only. The actual merge is handled by the spec-sync agent which understands markdown semantically.

Single-file constraint limits future complexity → If spectl grows beyond ~500 lines, split into a package. For now, simplicity wins.

No tests initially → The commands are simple enough to validate manually. Add tests if/when the tool stabilizes.
